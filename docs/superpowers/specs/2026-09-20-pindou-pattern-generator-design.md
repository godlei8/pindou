# 拼豆图纸生成工具 · 设计 Spec

日期：2026-09-20
状态：已与需求方逐节确认，待写实现计划

## 0. 一句话

上传一张图 → （可选）AI 重绘成适合拼豆的风格 → 生成带 MARD 色号的网格图纸 → 分析可拼性并给修复建议 → 导出 PNG / PDF + 材料清单。先给自己和朋友用，架构按"将来可能成为产品"来搭。

## 1. 目标与非目标

### 目标

- 出的图纸**能拼**：不只是像素化，要保证熨完不散、不断、不掉豆。这是与市面工具的核心差异。
- AI 重绘作为可选前置步骤，把照片变成粗轮廓、纯色平涂、无渐变的风格后再像素化。
- 生成后可手工修图（画笔 / 油漆桶 / 吸管）。没有任何转换器能一次到位，这是业界共识。
- 每次生成的参数、结果、可拼性评分、手工改动、实拼反馈全部落库，供后续校准算法。
- 多用户（账号密码 + 邀请码），每人独立的 AI 额度。
- 一条命令部署。

### 非目标（v1 明确不做）

- 微信登录、邮箱验证、找回密码、权限角色。
- 管理后台界面（管理员操作走命令行脚本）。
- 图纸社区、分享、点赞。
- 前端跑任何图像处理流水线（量化、色号匹配、graph cut）。手工编辑格子除外，见 §4.7。
- rembg 自动抠图。
- 按用户手上实际库存（每色多少颗）反解配色。
- 描边独立图层（v1 只做轻量的描边色锁定）。
- 独立 worker 进程（表建好，进程以后拆）。
- 前端单元测试。

## 2. 技术选型

| 层 | 选择 | 关键理由 |
|---|---|---|
| 后端 | Python 3.12 + FastAPI + Pydantic v2 | 可拼性优化是算法活，numpy/scipy 生态 |
| 图像处理 | numpy + Pillow + scipy.ndimage | 连通域、形态学都是现成的 |
| 色号分配 | `pyGCO`（graph cut / α-expansion） | 生成时抑制散点；LEGO 马赛克论文验证过的同构解法 |
| 色差 | 自写向量化 CIEDE2000 + OKLab | `colormath` 已停维护且逐点循环，14400 格慢到不能用 |
| ORM | SQLAlchemy 2.0 + Alembic | 抽象数据库，迁移可追溯 |
| 数据库 | PostgreSQL 16 | 多用户并发写；JSONB 存网格和报告；开发/生产同构 |
| 队列 | `jobs` 表 + `SELECT … FOR UPDATE SKIP LOCKED` | 不引入 Redis，几个人的量级够用 |
| 前端 | Vite + React + TypeScript | 纯 UI，所有计算在后端 |
| 认证 | bcrypt + HttpOnly session cookie | 比 JWT 简单，能真正登出 |
| 部署 | Docker Compose：db / api / web(nginx) | 一条命令 |

### 三条硬约束

1. **流水线只实现一次，在 Python 里。** 前端不缓存、不推算，后端返回什么画什么。避免两套实现结果对不上。唯一例外是手工编辑直接改写格子值（§4.7）——那是数据编辑，不存在算法可分歧。
2. **AI 是可选环节，可拼性是附加环节。** 二者任一失败都不能让"出一张图纸"这件核心事失败。
3. **色卡数据必须带出处。** 见 §11。

## 3. 整体链路

```
上传原图
  └─> [AI 重绘·可选] ──> 入 jobs 表 ──> API 进程内后台任务调 provider ──> 结果落 ai_renders（按输入哈希缓存）
        └─> 预处理（吸管抠背景、裁剪）+ 按输入类型分派下采样
              └─> 色卡受限 k-medoids 选色 → graph cut 分配色号
                    └─> 可拼性分析（连通域一次分解，导出全部指标 + confetti%）
                          ├─> 体检报告 + 修复建议（用户逐条 apply / reject）
                          ├─> 手工编辑（画笔 / 油漆桶 / 吸管，保存成新版本）
                          ├─> 超尺寸时底板分片（接缝落在低细节区）
                          └─> 渲染导出：PNG / PDF + 材料清单
                                └─> 参数、结果、评分、编辑、反馈全部落库
```

**用户视角只有一次等待**：上传 → 点一下 → 进度条 → 直接看到图纸。后端一个 job 把"AI 重绘 → 默认参数出图纸 → 可拼性分析"一口气跑完。之后调参数在已缓存的 AI 结果上重算，百毫秒级同步返回。不勾 AI 则跳过第一步，几乎不用等。

## 4. 图纸生成流水线

### 4.1 下采样、选色与分配

依据：[算法分析与优化](../../research/2026-09-20-algorithm-analysis.md)。该文档的调研结论已回填至本节，此处只记最终决策。

```
输入图
 ├─ A. 输入类型判定（网格检测：是否已是像素图 / AI 伪像素图）
 ├─ C1 普通图（卡通/插画/照片）：双边滤波 → 线性 RGB 面积平均下采样
 ├─ C2 像素图 / AI 伪像素图：网格相位检测对齐 → 格内众数采样
 ├─ D. 选色：色卡受限 k-medoids（OKLab 距离，簇心直接 ∈ 色卡，k ≤ 色数上限）
 └─ E. 分配：多标签 graph cut / α-expansion
        数据项 = ΔE00(格子, 色号)，平滑项 = λ·[相邻格色号不同]（Potts）
```

四个关键决策及理由：

- **下采样在线性 RGB 做面积平均**，不在 sRGB。市面工具普遍在 sRGB 平均，导致暗部偏亮、边缘发灰（"灰色毛边"是高频抱怨）。像素图走网格检测 + 众数，均值会凭空造出原图没有的颜色。
- **选色用色卡受限 k-medoids，簇心直接限定在色卡内。** 比"k-means 后再映射簇心"更干净——后者会出现两个簇心映射到同一色号需要去重。而市面工具清一色是"逐格匹配全色卡后按频次截断"，会吞掉眼睛高光这类小面积关键色。
- **分配用 graph cut 而非逐格独立最近色。** 散点是拼豆的头号敌人，而生成时预防优于事后清理——事后的多数滤波会磨掉合法的单格高光。LEGO 马赛克论文 Pixel2Brick 用同一方法解同构问题（固定色板 + 空间连贯）。`pyGCO` 现成可用，100×100 格 × 50 色号在秒级内。
- **λ（平整度）暴露为用户滑块。** λ=0 退化为纯最近色，即市面工具的行为——天然的对照组，也是算法回归测试的 baseline。

**抖动默认关闭**，开关保留并标注"会显著降低可拼性"。开启时仅在低梯度大面积区施加，且抖后仍跑连通域约束。

**描边保护**（v1 轻量版）：检测暗色细线格，在 graph cut 中锁定其标签为最近的深色色号。卡通图黑轮廓被匹配成杂灰是高频抱怨。

**尺寸推荐**：生成时并行算 2–3 个候选格数的缩略预览，标注各自会丢失哪些细节。流水线足够快，多算两档近乎零成本。

用户参数：长边格数、最多色数、**平整度 λ**、抖动开关。

### 4.2 背景处理

吸管点选 + 容差洪水填充 → 透明（空格）。不上 rembg：AI 重绘那一步的提示词本来就要求纯色背景，用上百兆模型解决一个上游已解决的问题不划算。

### 4.3 可拼性分析

**一次 4-连通域分解，派生全部指标。**

| 检查项 | 算法 | 为什么要管 |
|---|---|---|
| 整图连通性 | 非空格做 4-连通标记，组件数 > 1 报警 | 成品会散成几块 |
| 孤立单豆 | 四邻域全空的格子 | 熨完粘不住 |
| 对角虚连 | 8-连通组件数 < 4-连通组件数 ⇒ 存在只靠对角"看起来连着"的部分，定位接触点 | 拼豆靠**边**相邻熔合，对角等于没连 |
| 单格宽细线 / 悬臂 | 十字结构元腐蚀一次，消失的格子即宽度 ≤ 1 的区域 | 熨完一掰就断 |
| 内部空洞 | 对空格做连通域，不与图像边界连通的即空洞 | 成品中间有洞 |
| 小色号 | 每色统计颗数，低于阈值（默认 10 颗，可配置）标记，算出并入最近色的 ΔE | 为几颗豆单独买一包不值 |
| **confetti%** | 无同色邻居的格子占全图比例 | 十字绣领域的成熟标定：<2% 可接受，>10% 极难做。是"图纸好不好拼"最直观的单一数字 |

**评分**：各项加权成 0–100。权重 v1 先给经验值，等实拼反馈攒够后回头校准。

**孤点保护**：用户可标记若干格为"保留"（眼睛高光这类合法孤点）。被标记的格子在 graph cut 中锁定标签，在清理与修复建议中豁免。业界共识是没有算法能自动分辨高光与噪点，所以这必须交给人。

### 4.4 修复建议

每条问题产出一个可执行 patch：

```json
{ "type": "isolated_bead", "cells": [[34,17]], "action": "merge_to_neighbor", "target_color": "B12", "delta_e": 3.2 }
```

前端逐条 apply / reject，**不自动改**。修复本质是拿视觉保真度换结构强度，只有用户看着图才能定。apply 后生成新版本 pattern（见 §5），增量重跑分析。

**悬空 / 对角虚连类问题，首选动作是"补透明豆桥"**（`action: "bridge_with_clear"`，MARD T01 / Perler Clear）。这是实拼社区的标准解法——在空隙里塞透明豆当结构骨架，熨完几乎隐形，**保持图形不变**。"并入邻色"和"删除"会改变图形，作次选。市面工具无一提供这个动作。

### 4.5 底板分片

底板尺寸为可配置参数，默认值在实现时确认国内常见规格后填入。

算法：在网格上找横竖切割线，候选线代价 = 它切断的同色连通边数，选代价最小者，允许在目标尺寸附近 ±3 格浮动（可配置）。输出每片独立图纸 + 一张总装配图。无解（图比板小、无合理切线）时退化为不分片 / 均匀切分，并在报告中注明。

### 4.6 渲染导出

- **PNG**：网格线 + 每格印色号 + 边缘坐标轴。
- **PDF**：1:1 实际尺寸（5mm 豆 = 每格 5mm），超 A4 自动分页并打拼接标记与页间重叠区。
- **材料清单**：色号、色名、颗数、预估包数。

**可读性规则**（每条都对应一条真实投诉，不是锦上添花）：

- 网格线必须落在整数像素上。1pt 线被抗锯齿摊到两三个像素会变成"一层灰雾"，这是实际用户反馈的原话。
- 色号文字留边距、不顶格线，否则相邻格的编号会粘连成一串。
- 辅助线按底板刻度：每 5 格虚线、每 10 格实线——要和用户手里板子的刻度对得上。
- 空格 / 透明格的色号可隐藏（大片白底印满 T01 会让图纸显得很杂）。
- 相近色号避免分配相近的标注符号（十字绣软件的成熟规则）。

### 4.7 手动编辑

"生成后不可编辑 = 死图"是竞品差评的高频区，业界共识也是**没有任何转换器能一次到位**。v1 提供最小编辑能力：

- **单格改色**：点/拖，从当前工作色板里选色
- **油漆桶**：4-连通同色区域整片换色
- **吸管**：从画布取色号（差评原话："画图的时候没法吸色号很鸡肋"，顺手做了）
- **橡皮**：格子置空
- **孤点保护标记**：把格子标为"保留"（见 §4.3）
- 本地撤销 / 重做

**提交模型**：编辑在前端累积成一个待提交的改动集，点保存才落库，生成一个新版本 pattern。不是每一笔都建一行——否则版本树会被几百次笔画撑爆。

**关键约束：改动集以「格子 → 色号」的显式列表提交，不提交"在 (x,y) 执行油漆桶"这样的操作意图。** 后端只负责存下用户实际看到的结果、重跑可拼性分析，绝不重新执行填充算法。这样前后端不存在任何算法分歧的可能。

这也界定了 §2 那条硬约束的边界：**前端可以直接改写格子的值，但永远不许重新跑量化、色号匹配或 graph cut。** 前者是数据编辑，没有算法可分歧；后者是流水线，只能在 Python 里有一份实现。

## 5. 数据模型

原则：**凡是将来校准可拼性权重要用到的，现在就落库。**

```
users             id, username, password_hash, ai_quota, ai_used, created_at
invite_codes      code, created_by, max_uses, used_count, expires_at

projects          id, user_id, name, source_image_path, created_at
  ai_renders      id, project_id, provider, model, style_preset_id, prompt, params(JSONB),
                  input_hash, output_path, status, cost, error, created_at
                  —— 按 input_hash + style_preset 命中缓存，不重复扣额度
  patterns        id, project_id, ai_render_id(nullable), parent_id(nullable),
                  params(JSONB)        格数 / 色数 / 平整度 λ / 抖动 / 色卡 / 背景处理 / 保护格列表
                  grid(JSONB)          二维数组，值为 palette_colors 索引或 null
                  color_stats(JSONB)   每色号颗数
                  buildability(JSONB)  {score, confetti_pct, issues:[{type, cells, action, target_color, delta_e}]} 或 null
                  origin               'generated' | 'patched' | 'edited'  本版本怎么来的
                  applied_patch(JSONB) origin=patched 时：应用了哪条建议
                  manual_edits(JSONB)  origin=edited 时：[{cell:[x,y], from, to}] 显式改动列表
                  created_at
    feedback      id, pattern_id, user_id, kind(断裂/掉豆/色差/难数格), cells(JSONB), note, created_at

palettes          id, brand, name, version
  palette_colors  id, palette_id, code, name, rgb, lab（预算好）, in_sets(JSONB)

style_presets     id, name, prompt, params(JSONB), version, is_active
                  —— AI 重绘的提示词资产，存库可版本化，不硬编码

jobs              id, type, payload(JSONB), status(pending/running/done/failed),
                  attempts, locked_at, result(JSONB), error, created_at
```

决策记录：

- `grid` 用 JSONB 不用 bytea：120×120 才几十 KB，可查可索引。
- 修复用 `parent_id` 链成版本树，不原地改：`applied_patch` 攒起来就是"哪类修复用户真的认"的数据。UI 上按 project 折叠版本。
- 手动编辑同样进版本树，但**一次保存 = 一个版本**，不是一笔一个。`manual_edits` 记的是显式格子改动列表——它同时也是宝贵数据：用户手工改的地方，正是算法没做对的地方。
- `palette_colors.lab` 预算存储：匹配是热路径。
- `feedback.cells` 精确到格子：反推规则漏洞要靠坐标。
- 导出文件不建表，磁盘按 `pattern_id` 存。
- 大文件（原图、AI 图、PDF）走磁盘，库存路径。存储层抽接口，将来换 OSS 只改实现。

## 6. AI 重绘层

### 6.1 Provider 抽象

```python
class ImageProvider(Protocol):
    name: str
    def redraw(self, image: bytes, style: StylePreset, extra: dict) -> RedrawResult: ...
    def estimate_cost(self, style: StylePreset) -> Decimal: ...
```

- `providers.yaml` 配置每家的 base_url / api_key 环境变量名 / model / 适配器类型。
- v1 两个适配器：`openai_compatible`（火山方舟、百炼兼容模式、任何中转网关）和 `dashscope_native`（通义万相原生异步任务接口：提交 → 轮询）。加一家 = 加一个几十行文件。
- 风格预设的提示词目标：粗轮廓、纯色平涂、无渐变、无抗锯齿、简化细节、纯色背景。存 `style_presets` 表，随调研和反馈迭代。
- **AI 的输出一律按"伪像素图"对待，强制过 §4.1 的 C2 路径（网格相位检测 → 众数采样 → 色卡吸附）。** 扩散模型在连续潜空间工作，没有离散像素概念，直出的"像素图"格子大小不一、边缘带抗锯齿柔化色、纯黑轮廓里混十几种灰——拿来直接用就是社区痛骂的"看着像、根本拼不了"。这条不是优化，是底线。

### 6.2 额度

- 提交 AI 任务时**先扣后跑**，失败退回，防并发刷穿。
- 命中 `ai_renders` 缓存不扣。
- 管理员加额度 = 命令行脚本。

### 6.3 失败处理

- provider 超时 / 报错重试 2 次；仍失败 job 标 failed、退额度、前端提示"可跳过 AI 直接出图"。
- 返回图无法解析：同上，原始响应存 `job.error`。
- 服务启动钩子：把 running 的 job 标 failed 并退额度。

## 7. API

REST，前缀 `/api`，session cookie 鉴权。

```
POST /auth/register   {username, password, invite_code}
POST /auth/login · POST /auth/logout · GET /auth/me

POST /projects                          上传原图
GET  /projects · GET /projects/{id}     列表按 project 折叠版本

POST /projects/{id}/generate            {use_ai: bool, style_preset_id?, params?}
                                        入 jobs 表，返回 job_id；job 完成后 result 含 pattern_id
GET  /jobs/{id}                         轮询状态

POST /projects/{id}/patterns            {source: original | ai_render_id, params}
                                        同步重算，返回完整 pattern
GET  /patterns/{id}
POST /patterns/{id}/apply-patch         {issue_index} → 新版本 pattern
POST /patterns/{id}/edits               {edits:[{cell,to}], protected_cells?}
                                        一次保存提交整个改动集 → 新版本 pattern
                                        后端只写入 + 重跑分析，不重放填充算法
POST /patterns/{id}/feedback            {kind, cells, note}
GET  /patterns/{id}/export              ?format=png|pdf&board=WxH

GET  /palettes · GET /palettes/{id}/colors
GET  /style-presets
```

**首次生成走 job（含 AI 时要等十几秒），调参走同步接口（百毫秒级）。** 两种耗时特征不同，不强行统一。

参数校验上限：上传 ≤ 20MB，仅 jpg/png/webp；长边 ≤ 200 格；色数 ≤ 64。

## 8. 前端

四个页面一条主线：

```
登录/注册
  └─> 我的项目（列表，按项目折叠版本）
        └─> 项目工作台
              ├─ 左：原图 / AI 结果切换，风格预设，"生成"按钮（含 use_ai 勾选）
              ├─ 中：图纸 canvas，问题格子高亮，点击看问题类型
              │      编辑工具条：画笔 / 油漆桶 / 吸管 / 橡皮 / 保护标记 / 撤销重做 / 保存
              ├─ 右：参数面板（格数、色数、平整度 λ、抖动、吸管抠背景）
              │      可拼性评分 + confetti% + 问题列表（逐条 apply / reject）
              │      材料清单
              └─ 底：导出（PNG / PDF，选底板尺寸）、实拼反馈入口
```

- 参数改动防抖 300ms 后打 `POST /patterns`，整份 pattern 重画。
- canvas 用 OffscreenCanvas。
- 编辑态：改动累积在前端内存，未保存时有明显标识；切换参数会丢弃未保存改动，需二次确认（参数重算必然覆盖手工改动，这个冲突躲不掉，只能提示清楚）。
- 实拼反馈 = 同一 canvas 框选格子 + 选问题类型 + 备注。

## 11. 待定项

- 底板尺寸默认值：实现时确认国内常见规格。
- 可拼性评分权重与 λ 默认值：v1 经验值，攒实拼反馈后校准。
- **MARD 色卡真值**：这是全项目风险最高的一项。厂商不公布官方色值，市面所有工具的色卡都是社区/淘宝抄来的，已知某开源项目的色值里混入字母 O 当十六进制放了九个月。做法：以 `maxcleme/beadcolors`（含 Lab）与 `Zippland/colorSystemMapping.json` 交叉校验，冲突处标记存疑并留待实物比对。**每个色值都要记来源。** 算法再好，色卡错了全盘皆输。
- 套装划分（144 / 221 / 291）与 `in_sets` 数据：实现时核实。
- 抖动开启态的实现（仅低梯度区 + 有序/蓝噪声 + 抖后连通域约束）：不在算法核心计划一内，`Params.dither` 先只接受 False；在后端服务计划前作为独立小任务补上。
- §4.6 "相近色号避免相近标注符号"：v1 图纸直接印色号文本而非符号，该规则暂不适用；若将来改用符号图例再启用。

### 算法核心实现后的实测发现（2026-09-20，见 `backend/scripts/benchmark.py`）

- **平整度 λ 默认值定为 2.0**，依据是 10 张黄金样本的基准比较：λ=2.0 在每张图上的 confetti 都不劣于 1.0 且不损失色数；λ=3.0 开始吃掉色号（logo 6→5、yellow 5→4），属保真度损失。
- **MARD 色卡两源冲突 79/291（27%）**，远超预期。其中 ΔE00≥10 的有 10 处，最严重 Q5（beadcolors #4F5E5B 灰绿 vs zippland #76CEDE 浅青，ΔE=38）、Q2（ΔE=27）、R6（ΔE=22）——这几个必有一源是错的。当前以 beadcolors 为准、`alt_hex` 保留另一值备查。**买到实物后优先比对这 10 处。**
- **抗锯齿边会吃掉色号预算**：卡通样本视觉上只需 5 色（白底/黄脸/黑边/白眼/红嘴），但 max_colors=12 时算法用满 11 色，多出的都花在描边的过渡色上。这正是调研里"随机冒出原图没有的颜色"那条抱怨的成因。双边滤波 + λ 只能缓解，未根治。
- **小特征（瞳孔）在低格数下会糊**：400px 原图的 15px 瞳孔在 48 格下仅 1.8 格，被过渡色吃成灰而非纯黑。对应调研里"眼睛不对称/高光点不对"的抱怨。尺寸推荐应对这类图给出更高格数建议。
- **像素图输入会自我保护**：4 色像素图的色间 ΔE 极大，数据项彻底压过平滑项，λ 从 0 加到 3 输出完全不变。不需要为像素图单独关掉 graph cut。
- 本节数据可用 `python scripts/benchmark.py --smoothness <λ>` 复现。

### 连续调参只留最后一版（2026-09-21）

原来每次调参（防抖 300ms 后）都存一个新版本，拖一下滑块停一下就是一版，
一轮调参版本列表能多出七八个几乎一样的。

**没有做成"拖滑块只预览、手动确认才保存"。** 下载、手改、一键修复都要基于已保存的版本，
预览态下它们要么拿到旧版本、要么还得偷偷先存一版；忘了保存就离开，调好的参数就丢了。

**做法：照常立刻保存，但一段连续调参里新结果替换上一个过渡版本。**
效果是一段连续调参最多新增一版，下载和编辑拿到的永远是屏幕上这一版。

- 前端记住"这段调参里上一次算出来的是哪版"，下次请求带 `replaces`。
  载入、切版本、手改、修复、AI 出图都会清空这个记录——之后第一次调参必须新增，
  不能把用户刚选中、刚做出来的版本替换掉。
- 后端复核，四条全满足才删（`patterns.discard_draft`）：同一项目、`origin == generated`、
  没有子版本（`parent_id` 是 SET NULL，删了会留孤儿）、**没有实拼反馈**
  （`feedback` 是 CASCADE，删了会把反馈一起删掉，那是标定评分唯一的真实数据）。
  任何一条不满足就只新增不删除。
- 新增与删除同一事务，出图失败不会误删。
- 重算串行化：计算中只记下最新参数，中间的跳过。否则慢请求后到会用旧结果盖掉新的，
  两个请求还会争着替换同一版、漏删一版。

### AI 收益的预判信号（2026-09-21，阈值待标定）

工作台在"原图出的图纸评分 ≥ 85"时提示 **"这张图可能不需要 AI"**（`SourcePanel.tsx`）。

阈值 85 取自目前仅有的两个真实对照，属**暂定值**，需要攒实拼反馈后重新标定：

| 源图 | 原图图纸 | AI 重绘后 | 结论 |
|---|---|---|---|
| avatar.jpg（JPEG 动漫头像） | 89.2 分 / 散点 5.47% | 80.4 分 / 8.26% | AI 让它变差 |
| 提示词实测那张 | 81.6 分 / 7.90% | 87.4 分 / 6.03% | AI 让它变好 |

**不要改成按"源图色数/平坦度"判断。** 实测过这条路：

| 图 | 主色数 | 平坦度 | 原图图纸评分 |
|---|---|---|---|
| avatar.jpg（AI 让它变差的那张） | 35 | 0.198 | 89.2 |
| 已经是平涂的样本 | 4 | 0.988 | 89.0 |
| 典型照片 | 0 | 0.000 | — |

avatar.jpg 是 JPEG，压缩噪点把平坦度毁了，量出来和照片没区别——
**色数检测恰恰抓不到唯一那个真实案例**，而图纸评分两种情况都能抓到。
评分还有一个优势：它是已经算好的量，且 confetti 阈值本身对过十字绣行业基准。

### 前端计划阶段的两处决定（2026-09-20）

- **canvas 不用 OffscreenCanvas**（spec §8 原文提到）。OffscreenCanvas 主要解决"在 worker 里绘制不阻塞主线程"，而图纸最大 200×200 格、主线程绘制在毫秒级，引入 worker 只增加复杂度不带来收益。改为普通 canvas + 把"算坐标"与"调 ctx"分离（jsdom 没有 2d 上下文，这样才测得了）。
- **AI 重绘的完整前端交互（风格预设选择 + job 轮询进度条）延后**。后端接口齐备，但开发期没有 API key，`FakeProvider` 下的体验与"跳过 AI"无异，做了也验证不了。等拿到真实 key 后单独做一轮。

### 浏览器验收发现的可拼性评分缺陷（2026-09-20，待修）

真实浏览器跑通全链路时发现：**接受一条修复建议后，各项指标全面改善，总分反而从 10 降到 6.5**。

用透明底细斜线样本（44×44 格）实测，那条建议补了 40 颗透明豆把断开的部分连上：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| confetti | 39.34% | 29.63% ↓ |
| 孤立豆 | 48 | 41 ↓ |
| 对角虚连 | 47 | 41 ↓ |
| 细线占比 | 0 | 0.173 ↑ |

两层原因：

1. **评分饱和**。不连通(-30)、孤立(-20)、对角(-15)、confetti(-25) 四项扣分在这种图上全部触顶，真实的改善一分都反映不出来；唯一没触顶的细线项新增 -3.5，于是总分下降。评分在"很糟"的区间里失去了分辨率，无法奖励进步。
2. **透明豆桥被当成"细线易断"扣分**。补的桥天生就是 1 格宽，但它是结构支撑，不是脆弱悬臂——`thin_line` 检测应当把起桥梁作用的透明豆排除，或单独计权。

这正是 spec 早先标注的"权重 v1 先给经验值、攒反馈后校准"要处理的事，现在有了具体数据。修的时候建议：① 把封顶改成软饱和（如对数衰减），让改善始终可见；② `thin_line` 排除 `role=clear` 的格子。
